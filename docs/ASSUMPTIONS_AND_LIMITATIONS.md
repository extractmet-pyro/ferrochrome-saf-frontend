# FeCr-TWIN — Assumptions and limitations

**Status: SYNTHETIC / NOT PLANT-VALIDATED.** Every number produced by this release comes from a synthetic
virtual plant ("Industry-X", 45 MVA closed AC SAF by default). Nothing here is a design limit for a real furnace.

## 1. Scope

| Item | Status |
|---|---|
| HC FeCr (charge chrome) in AC three-electrode SAF | Implemented |
| Open, semi-closed, closed roof | Implemented (air infiltration, freeboard combustion, gas train label) |
| Pre-reduced / hot chromite feed | Implemented as material variant + feed temperature (scenario F) |
| Capacity classes 9–81 MVA | Implemented by rule-of-thumb geometry scaling (CALIBRATION-REQUIRED) |
| DC SAF | NOT IMPLEMENTED (different electrical physics; separate configuration needed) |
| Low-carbon FeCr route | NOT IMPLEMENTED (different process) |
| Closed-loop control / PLC writes | NOT IMPLEMENTED by design; `ADVISORY_ONLY=false` is refused at start-up |
| FactSage / ChemApp equilibrium | Adapter boundary only; no proprietary database bundled |

## 2. Physical model assumptions

1. **Lumped zones.** Burden (2 zones), coke bed, slag, metal, freeboard; uniform temperature and composition
   inside each zone. No 3-D current, flow or temperature fields.
2. **Enthalpy data** are approximate Maier–Kelley fits; spinel (FeCr2O4, MgCr2O4), CrO, Cr7C3, dissolved C,
   P2O5 and latent heats of slag and metal are CALIBRATION-REQUIRED. Enthalpies of mixing are neglected.
3. **Mineralogy** of chromite is approximated by end-member allocation (FeCr2O4, MgCr2O4, MgAl2O4 + free
   oxides). Replace with XRD/QEMSCAN mineralogy for site use.
4. **Activities** use constant activity coefficients. Real Cr2O3/CrO activities depend strongly on slag
   chemistry and oxygen potential; a licensed thermodynamic database is recommended for commissioning.
5. **Kinetic pre-exponential factors** were tuned so the synthetic nominal case falls inside published HC FeCr
   ranges (SEC 3.2–3.5 MWh/t, Cr recovery ~ 88–92 %, slag Cr2O3 ~ 8–10 %, metal C ~ 6.5–7 %, Si ~ 3–4 %).
   They have **not** been fitted to any plant. Parameter identifiability analysis (`twin/uncertainty.py`) shows
   several kinetic combinations cannot be separated using normal plant measurements; dependent quantities
   (e.g. undissolved-chromite inventory) are therefore reported as model estimates with uncertainty, not facts.
6. **Electrical**: reduced-order resistive network (coke-bed tip path ∥ burden side path) with constant
   per-phase reactance; ρ_cb0 is auto-calibrated to the design resistance; harmonics and arc dynamics are
   not modelled (arc fraction lumped into coke-bed heating).
7. **Gas**: quasi-steady (no gas hold-up dynamics in the burden); counter-current exchange by effectiveness;
   no SiO(g) or Mg/Zn vapour transport; sulphur leaves only with metal and slag (no SO2/H2S/COS).
8. **Dust**: empirical carry-over law; total Cr only — Cr(VI) speciation is not modelled and must be measured.
9. **Freeze lining** is quasi-steady without slag mass exchange.
10. **Tapping** is an instantaneous event; tap-hole flow dynamics, slag/metal separation in the launder and
    ladle heat losses are not modelled.
11. **Lab assays** are modelled as tapped-stream analyses with Gaussian noise; sampling bias is not modelled.
12. **Static balance** uses surrogate recoveries (η_Cr, Si) calibrated to the dynamic twin, not to a plant.

## 3. Data and ML assumptions

* The ML training campaign is generated by the twin with a **hidden, deliberately introduced mismatch** (fines-
  dependent chromite mass transfer, altered slag current path, coke reactivity drift). Good hybrid metrics
  demonstrate the pipeline, **not** real-world accuracy.
* Lag-1 lab features make the Cr-recovery and slag-Cr2O3 residual models benefit from autocorrelation; on a
  real plant, accuracy will be lower and must be re-established with chronological validation.
* OOD threshold (1.25 × 99th percentile Mahalanobis distance) is a demo setting.

## 4. Control assumptions

* MPC is linearised (step responses identified from the twin each execution, single move held over a 6 h
  horizon). Nonlinearity is handled by receding horizon and a nonlinear verification run, not by a nonlinear
  optimiser over the full model.
* Weights, horizons, move limits and constraint limits are DEMO-ONLY and must be set at commissioning.
* The baseline "operator policy" used in comparisons is a simple electrode-depth-based coke rule, not a
  representation of any specific plant's practice.

## 5. Software and deployment limitations

* Simulation sessions live in memory; a restart (including Render free-tier sleep) loses them. Scenarios,
  recommendations, audit, model metadata and lab entries persist in the database; ML model files persist on
  the configured disk (`MODEL_DIR`).
* The in-process job pool suits a single instance. Multi-instance scaling needs a shared job queue/worker and
  sticky sessions or an external session store.
* Rate limiting is in-process per IP; use the platform's edge rate limiting in production.
* JWT HS256 with seeded role accounts is suitable for demonstrations; production deployments should use the
  customer's OIDC identity provider (adapter point in `core/security.py`).
* Postgres was not available in the build environment; the SQLite path was tested end-to-end, the Postgres
  path (psycopg3 driver, Alembic migration) is NOT EXECUTED here and must be verified on first deployment.
